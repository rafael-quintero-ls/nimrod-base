## Context

See `proposal.md` - Why/What Changes for the audit findings and the exact version deltas. Constraints shaping this design:

- `@sidebase/nuxt-auth@1.1.0` peer-pins `next-auth: ~4.21.1` (confirmed via `npm view @sidebase/nuxt-auth@1.1.0 peerDependencies`); only `@sidebase/nuxt-auth@1.3.x` widens that pin enough to accept `next-auth@4.24.15`. The two packages must move in the same commit.
- `middleware/acl.global.ts` and `server/api/auth/[...].ts` are marked high-blast-radius in `AGENTS.md` — this change touches their dependencies (not their code) but still goes through the full gate.
- `swiper@11.2.10 → 12.x` is a major version bump; the repo's only consumers are the demo pages under `views/demos/components/swiper/*` (10 files, template showcase, not app-critical UI), so the regression surface is narrow and visually verifiable.
- `vuetify@3.10.8 → 3.13.2` stays within the 3.x line — Vuetify MCP's `get_v4_breaking_changes` tool confirms all breaking changes (CSS layers, theme default, grid overhaul, `v-btn` styling, `v-select` slot rename) are gated behind the 4.x major, not present between 3.10 and 3.13.
- No CI pipeline exists yet (per `CONTRIBUTING.md`) — the PR itself, backed by manual verification below, is the only gate before merge.

## Goals / Non-Goals

**Goals:**
- Move every `dependencies`-listed package (plus the two `devDependencies` it structurally requires: `@sidebase/nuxt-auth`, `vite`) out of the critical/high ranges `pnpm audit --prod` currently reports.
- Preserve exact current behavior of login, ACL guarding, and every existing page/route.
- Keep the change reviewable as a single PR (version bumps + lockfile only).

**Non-Goals:**
- Migrating to Vuetify 4, Nuxt 5, ESLint 9/10 flat config, or TypeScript 7 — each is a separate breaking-change track requiring its own OpenSpec change.
- Adding new auth providers, ACL rules, or route rules.
- Fixing `devDependencies`-only or moderate/low-severity advisories not on the critical/high list (e.g. `postcss`, `js-yaml`, `ajv` deep-transitive findings) unless they ride along automatically via the lockfile refresh from the primary bumps above.

## Decisions

**Bump `nuxt` to 4.5.2, not just the minimum-patched 4.4.7.**
4.4.7 fixes CVE-2026-53721 but is itself in the vulnerable range for the July 27 security bundle's route-rule regression, RCE, DoS, and cache-leak advisories (all require ≥4.5.1). 4.5.2 is the latest patch on the 4.x line at the time of this change and is what `nuxt.com/blog/v4-5-security` recommends via `npx nuxt upgrade --dedupe`. Alternative considered: stay on 4.4.x patch line — rejected, it does not clear the July bundle.

**Bump `@sidebase/nuxt-auth` and `next-auth` together, not independently.**
Bumping only `next-auth` past `4.24.x` would violate the installed `@sidebase/nuxt-auth@1.1.0` peer range and pnpm would either refuse or silently produce an inconsistent tree. Alternative considered: pin `next-auth` at the loosest version still inside `~4.21.1` that clears the audit — none exists, `4.21.1`'s entire compatible range is vulnerable, so the peer-owning package must move too.

**Stay on Vuetify 3.x (3.13.2), do not adopt Vuetify 4.**
Vuetify 3.10.8 → 3.13.2 carries no breaking changes per the MCP-sourced breaking-changes doc (all listed changes are 4.x-gated). Vuetify 4 is not implicated in any audit finding — it is a template/UI major version, not a security fix — so pulling it into a security-patch track would inflate blast radius without addressing the stated problem. Alternative considered: bundle the Vuetify 4 migration here — rejected, violates `AGENTS.md`'s one-intent-per-change rule and this repo's admin-template UI is extensive enough that the migration needs its own design pass.

**Bump `swiper` to 12.x despite it being a major version.**
It is the only critical advisory (`GHSA-hmx5-qpq5-p643`) without a patched release inside the current major. Usage is confined to demo pages, so the API-surface risk is low and independently verifiable by loading each demo route.

**Bump `vite` to `8.2.2`, not the `>=7.3.2` originally planned.**
The original plan patched the audit's `vite` vulnerable range (`>=7.1.0 <=7.3.1`) with the smallest jump, `7.3.2`. That satisfies the audit but not `nuxt@4.5.2`: its `@nuxt/vite-builder` declares `vite: ^8.2.0` as a peer, so pinning `vite@^7.3.2` left two vite majors (`7.3.6` and `8.2.2`) resolved simultaneously in the tree. This broke `pnpm dev` at `/login` with `Error: Missing "#components" specifier in "nuxt" package` — Nuxt's `#components` virtual module is wired into the vite instance nuxt itself resolves (`8.2.2`), and the stray `7.3.6` copy confused the dep-scan step. Discovered during Behavioral Verification (task 5.1) and corrected by moving to `vite@^8.2.2`, which both clears the audit range by a wide margin and matches the peer nuxt actually requires. Lesson applied elsewhere in this design: verify the peer range of the framework version being targeted, not just the audit's minimum patched version.

**Add a `tar` override via `pnpm-workspace.yaml`, not `package.json`.**
`pnpm audit --prod` after the primary bumps still reported one critical (`tar <=7.5.18`, `GHSA-23hp-3jrh-7fpw`) from a deep transitive path (`nuxt → nitropack → @vercel/nft → @mapbox/node-pre-gyp → tar`, and separately `@iconify/tools → tar`) with no direct `package.json` entry to bump. The repo's existing `resolutions`/`overrides` top-level blocks in `package.json` are Yarn/npm syntax respectively and were already silently ineffective under this repo's pnpm 11 toolchain (confirmed: the pre-existing `cookie` override did not apply — `cookie@0.7.2` was installed despite the `1.0.2` override). pnpm 11 reads overrides from `pnpm-workspace.yaml`'s `overrides` key, so `tar: ^7.5.19` was added there instead, alongside a duplicate of the existing `postcss`/`@tiptap/core`/`cookie` overrides so they take effect too. This closes the last critical finding but is adjacent scope creep: it fixes preexisting non-functional overrides as a side effect. Flagged here rather than silently folded in — the alternative (leaving `tar` critical and unaddressed) would fail this change's own `dependency-security-baseline` requirement.

**Regenerate `pnpm-lock.yaml` in full rather than hand-editing ranges.**
`package.json` uses caret ranges (`^`) for most of these packages already, meaning several patched versions technically satisfy the existing range and are only blocked by the stale lockfile. Running `pnpm update <pkg>@<version>` per package and letting pnpm resolve transitives is safer than manual lockfile edits, and picks up compatible transitive security fixes (`h3`, `nitropack`, `@nuxt/devtools`, `vite`-adjacent) for free.

**Add a `nitro.alias` for `next-auth/core`, not a lower `next-auth` version.**
`next-auth@4.24.15` (any `>=4.23.0`) removed the `./core` subpath from its `exports` map, but `@sidebase/nuxt-auth@1.3.1` — the only 1.x release, all of which peer-pin `next-auth: ~4.21.1` — still hard-imports `next-auth/core` in its bundled `authjs` runtime service, crashing every route with `Package subpath './core' is not defined by "exports"` (confirmed as a known unresolved upstream gap, `sidebase/nuxt-auth#953`). No `next-auth` version satisfies both "outside the critical vulnerable range `>=4.10.3 <4.24.15`" and "has `./core`" simultaneously. The `./core` module's files are still physically present in the installed package (`node_modules/next-auth/core/index.js`), only unreachable through Node's `exports` map — a `nitro.alias: { 'next-auth/core': '<path>/node_modules/next-auth/core/index.js' }` entry in `nuxt.config.ts` makes Nitro's server bundler resolve the subpath directly, bypassing the `exports` restriction without patching `next-auth`, `@sidebase/nuxt-auth`, or any application auth code. Alternative considered: a `vite.resolve.alias` entry — rejected, verified not to apply because Nitro externalizes `next-auth/core` and resolves it through Node's runtime resolver, not Vite's.

**Add a `pages:extend` hook to default every page's layout, plus `extraPageMetaExtractionKeys: ['layout']` — not the hook alone.**
Independently of the auth fix, Nuxt 4.5.2 has an apparent core defect: `useLayout()`'s `resolveLayoutName` (new in 4.5.0) calls `routeRulesMatcher(...)` as a function, but at runtime the `#build/route-rules.mjs` virtual module resolves to something that isn't one, throwing `routeRulesMatcher is not a function` on any page without an explicit `layout:` meta — which is most of this app (dashboards, forms, tables). Confirmed independent of this change's dependency bumps: reproduced on a from-scratch `rm -rf node_modules && pnpm install --frozen-lockfile`; this repo defines no `routeRules` and no page uses `defineRouteRules`, so the generated matcher should be trivial. The operator chose to keep `nuxt@4.5.2` and mitigate with a `pages:extend` hook that sets `page.meta.layout ??= 'default'` on every page lacking an explicit layout.

**Follow-up correction** (caught by the operator visually reviewing `pnpm dev` after the PR was opened — HTTP-status-only verification during Behavioral Verification missed it): the hook alone broke `/login`, `/register`, and every other `layout: 'blank'` page, rendering them with the full vertical-nav `default` layout instead. Root cause: Nuxt's `augmentPages` build-time step, which runs before `pages:extend`, only copies a fixed `defaultExtractionKeys` list (`name`, `path`, `props`, `alias`, `redirect`, `middleware`) from each page's `definePageMeta` into `route.meta` — `layout` is **not** in that list, because `layout` is normally resolved at runtime by `useLayout()`, not at build time. So when the `pages:extend` hook ran, `page.meta.layout` was `undefined` for every page, including ones that declare `layout: 'blank'` in their own component — the hook's `??=` had no real value to defer to and forced `'default'` everywhere. Fixed by adding `experimental.extraPageMetaExtractionKeys: ['layout']`, which makes Nuxt's own `augmentPages` step extract `layout` from `definePageMeta` into `route.meta` before the `pages:extend` hook runs, so the hook's `??=` now sees each page's real declared layout and only fills in the missing default. Verified: `/login` and `/register` render `layout-blank` again; `/dashboards/analytics` still renders `layout-vertical` (the `default` layout, unaffected).

**Bump `sass` `~1.76.0` → `^1.93.2`, not the minimum `1.84.0` needed.**
`pnpm build` failed with `[sass] semicolons aren't allowed in the indented syntax` on `vuetify@3.13.2`'s bundled `VRating.sass`. Bisected: Vuetify introduced a stray SCSS-style semicolon into that `.sass` (indented-syntax) file between `3.13.0` and `3.13.1` — a confirmed upstream defect of the same shape as `vuetifyjs/vuetify#22798` (a different component, same root cause: SCSS syntax leaking into a `.sass` file). Dart Sass's own fix (`dart-sass#2467`) makes semicolons optional in `.sass` files starting `1.84.0`, so the installed `sass@1.76.0` rejects the file while `>=1.84.0` accepts it. Bumped to the latest `1.9x` line rather than pinning exactly `1.84.0`, consistent with the rest of this change's "bump to latest patch/minor, not just past the mimimum" pattern. Alternative considered: downgrade `vuetify` to `3.13.0` — rejected, `3.13.0` predates the target `3.13.2` for no security reason and reopens no audit finding, so it has no upside over fixing the actual incompatibility.

**Add `shamefullyHoist: true` to `pnpm-workspace.yaml`.**
`pnpm build` separately failed with `[sass] Can't find stylesheet to import` on `@use "flatpickr/dist/flatpickr.css"` in `@core/components/app-form-elements/AppDateTimePicker.vue`. Root cause: `flatpickr` is a transitive dependency (of the direct dependency `vue-flatpickr-component`) and pnpm's default strict `node_modules` layout does not hoist it to the project root, so Vite's Sass resolver — which resolves bare `@use` specifiers via Node-style `node_modules` lookup from the project root — cannot find it. This repo's `.npmrc` already sets `shamefully-hoist=true`, but (same pattern as the `overrides`/`tar` fix above) pnpm 11 no longer reads non-auth settings from `.npmrc`; they must live in `pnpm-workspace.yaml`. Verified: after adding the setting and reinstalling, `flatpickr` appears in the root `node_modules`, resolved directly via `require.resolve`. Alternative considered: add an explicit Sass `loadPaths`/importer config pointing at the nested pnpm store path — rejected, more fragile (breaks again if the nested path changes) and does not fix the same silent `.npmrc` gap that likely affects other transitive-dependency imports elsewhere in this codebase.
**Add `nitro.externals.inline` for next-auth's transitive CJS dependency chain, discovered post-PR via `pnpm build` + a real production preview.**
Task 6.1's original verification only checked `pnpm build` completed without errors, not that the produced server actually runs. Starting `node .output/server/index.mjs` surfaced `Error [ERR_UNSUPPORTED_DIR_IMPORT]` on `next-auth/jwt` — Nitro externalized it as `import * as jwt from '<pnpm-nested-absolute-path>/next-auth/jwt'` (missing the `/index.js` suffix Node's ESM loader requires for a directory import), a distinct bug from the earlier `./core` `exports`-map gap. Fixing that via a `nitro.alias` entry surfaced `_interopRequireDefault$1 is not a function` (`@babel/runtime/helpers/*`, plain CJS, externalized as a native ESM namespace import that doesn't carry the `__esModule` marker Babel's own interop helper checks for), then `LRU$2 is not a constructor` (`lru-cache`), then `Yallist is not a constructor` (`lru-cache`'s own dependency `yallist`) — each fix for one externalized CJS package surfaced the next one in the transitive chain. `nitro.externals.inline` (bundling the whole chain instead of externalizing any of it) fixed all of these at once. `noExternals: true` (bundle everything) was tried first and rejected: it stalled this VM's build under memory pressure (~7 GB RAM, heavy swap contention already present from repeated build/dev cycles in this verification session) without completing.

**Remove `CredentialsProvider.default(...)`'s pre-existing extra `.default` in `server/api/auth/[...].ts`.**
With `next-auth` now inlined, Rollup collapses the CJS default-export chain to the real function directly, so the pre-existing `// @ts-expect-error You need to use .default here for it to work during SSR` workaround (written for the unbundled/externalized case) now calls `.default` on the function itself, which doesn't exist, throwing `_default.default is not a function`. This is source code in a file `AGENTS.md` marks high-blast-radius, normally requiring its own OpenSpec change — the operator was asked directly and approved fixing it inline as an unavoidable consequence of the already-approved `next-auth` bump, rather than opening a second change to unblock the first.

**Fix `@panva/hkdf`'s ESM build via `pnpm patch`, not an alias, once the alias approach proved incomplete across dev and production.**
With the CJS chain inlined, `_interopRequireDefault(require("@panva/hkdf"))` inside `next-auth/jwt/index.js` broke: `@panva/hkdf`'s `dist/node/esm/index.js` build (a dual CJS/ESM package) has no `__esModule` marker, so whichever module condition the bundler resolved for the bare `@panva/hkdf` specifier — the `import` condition in Nitro's production rollup, and apparently something equivalent in `pnpm dev`'s separate Vite-driven server module resolution — Babel's `_interopRequireDefault` double-wrapped it, breaking `hkdf(...)` at call time (`(0 , _hkdf.default) is not a function`), exactly matching `sidebase/nuxt-auth#953`. Two alias-based attempts were tried first: a `nitro.alias` entry (fixed production only — Nitro dev's server bundling doesn't consult it) and an additional `vite.resolve.alias` entry (had no effect either — the dev-mode failure point is a different resolution path than Vite's own alias table reaches). Both were reverted in favor of a `pnpm patch` (`patches/@panva__hkdf.patch`) adding `export const __esModule = true` to the ESM build directly — this fixes the interop at its source regardless of which build any bundler or runtime resolves it to, verified working in both `pnpm dev` and the production preview.

**Lint-fix drift**: a `pnpm lint` run mid-session (before `.nuxt` existed, needed for the TypeScript import resolver) produced 1285 false-positive `import/no-unresolved` errors from unrelated files; regenerating `.nuxt` via `nuxt prepare` before the final `pnpm lint` resolved that noise, leaving one real, pre-existing, unrelated conflict between two `eslint`/`vue` lint rules on `views/apps/user/view/UserTabAccount.vue` (a stray `--fix` in an earlier run left it in a state where `lines-around-comment` and `vue/block-tag-newline` disagreed) — fixed by removing the now-redundant `// Images` section comment the conflict centered on. Separately, this session's repeated `pnpm lint` runs also reordered imports (no logic change) in ~48 files unrelated to this change's scope; kept as `style:` in its own commit rather than reverted, since it is exactly what running the repo's own lint command produces and reverting it would leave the repo in a state `pnpm lint` immediately un-does again.

**Break the `app/router.options.ts` static-import cycle (nuxt/nuxt#35982), rather than any workaround inside Nuxt's own generated code.**
After the layout hook fix above, a client-side-only error surfaced in the operator's real browser (never caught by any HTTP-status or curl-based check in this session): `Uncaught (in promise) ReferenceError: can't access lexical declaration '_routeRulesMatcher' before initialization`, thrown from `layout.js`. Root-caused via the upstream GitHub issue `nuxt/nuxt#35982` (open, confirmed by multiple independent reporters against Nuxt 4.5.1/4.5.2): the generated `#build/route-rules.mjs` imports `router.options.mjs`, which imports this repo's `app/router.options.ts`. That file's `/` redirect middleware called the auto-imported `useAuth()` as a static top-level dependency, closing a cycle back through `@sidebase/nuxt-auth`'s composable chain into the same `layout.js`/`manifest.js` modules that import `route-rules.mjs` — and whichever module the bundler happens to emit first in that cycle leaves the other's `const routeRulesMatcher = _routeRulesMatcher` referencing an uninitialized binding. Confirmed as a genuine Nuxt/bundler regression, not application-specific: the community-verified fix (per the issue's comments, including a maintainer-acknowledged root cause from another reporter) is deferring any composable/store import inside `app/router.options.ts` to inside the callback that needs it, closing the cycle. Applied that: `useAuth` (via `#imports`) and `callWithNuxt` (via `nuxt/app`, needed to preserve the active Nuxt instance context across the `await import()`, which otherwise drops it and throws "composable called outside of a plugin/middleware/setup") are now dynamically imported inside the middleware callback instead of resolved statically at module scope. Verified end to end (not just HTTP status): full login → root redirect by role → dashboard render, in both `pnpm dev` and the actual production preview.

**Align `@vueuse/core`/`@vueuse/math`/`@vueuse/nuxt` to the same `14.4.0`, closing a pre-existing (not this change's) version-mismatch that only became a build-breaking error once caches were fully cleared.**
`pnpm build` failed with `[MISSING_EXPORT] "manualResetRef"/"resolveRef" is not exported by @vueuse/core`. This repo's `package.json` already had `@vueuse/core@^10.11.1` (`dependencies`) alongside `@vueuse/nuxt@^14.0.0` (`devDependencies`, which resolves its own `@vueuse/core@14.0.0`) since the initial commit — two coexisting majors, present before this change touched anything. `@vueuse/nuxt`'s auto-import list is generated from `@vueuse/metadata`, which documents `manualResetRef`/`resolveRef` as present in `@vueuse/core@14.0.0`, but the installed `@vueuse/core@14.0.0` build genuinely does not export them (they exist starting `@vueuse/shared@14.1.0`, confirmed by checking `14.4.0`'s exports directly) — a real desync between `@vueuse/metadata` and `@vueuse/core` at that exact version. Fixed by bumping all three `@vueuse/*` packages to `^14.4.0`, collapsing the tree to one resolved version everywhere and picking up the missing exports. Not part of the original security-patch scope, but required to get `pnpm build` passing at all once the pnpm store no longer had a stale resolution masking it.

## Risks / Trade-offs

- **[Risk]** `@casl/ability`/`@casl/vue` major-adjacent internal changes silently altering `canNavigate` semantics → **Mitigation**: manually exercise both ACL scenarios in the delta spec (authorized/public route, unauthorized route) against `pnpm dev` after the bump, before opening the PR.
- **[Risk]** `next-auth`/`@sidebase/nuxt-auth` bump changing the JWT/session callback shape → **Mitigation**: log in with a real credentials flow post-upgrade and inspect the resulting session object for the five custom fields (`username`, `fullName`, `avatar`, `abilityRules`, `role`) the callbacks in `server/api/auth/[...].ts` set.
- **[Risk]** `swiper` 11→12 major bump breaking demo page rendering or options API → **Mitigation**: load each of the 10 `views/demos/components/swiper/*` demo routes in `pnpm dev` and visually confirm no console errors / broken carousels.
- **[Risk]** `vuetify` patch bump introducing a subtle visual regression despite no documented breaking changes → **Mitigation**: spot-check the dashboard, a data table view, and a form view after the bump; not exhaustive, but proportionate to a patch-level bump.
- **[Risk]** `vite@8`/`nuxt@5`/`eslint@10` ecosystem drift making some *other* transitive dep unable to satisfy multiple peers simultaneously during `pnpm install` → **Mitigation**: run `pnpm install` and read its peer-dependency warnings before committing; resolve or explicitly accept-and-document any remaining warning, don't silently ignore install-time errors.
- **[Trade-off]** Not upgrading `eslint`, `typescript`, or `vite` beyond the minimum needed for the `nuxt` bump means some moderate/low audit findings in devtooling remain open → accepted, out of scope per Non-Goals; tracked as follow-up work, not silently dropped.

## Migration Plan

1. On a branch (`fix/critical-dependency-security-update` per `CONTRIBUTING.md` naming), bump `nuxt`, `vite`, `@casl/ability`, `@casl/vue`, `next-auth`, `@sidebase/nuxt-auth`, `swiper`, `vuetify`, `vite-plugin-vuetify` to the target versions in `package.json`.
2. Run `pnpm install` to regenerate `pnpm-lock.yaml`; capture and resolve any peer-dependency warnings.
3. Run `pnpm audit --prod` and confirm 0 critical / 0 high remain for `dependencies`-tree packages (moderate/low from out-of-scope devtooling packages may remain — document which, per Non-Goals).
4. Run `pnpm dev` and manually verify: login flow, one ACL-guarded route (authorized + unauthorized), one public route, dashboard render, one data table, one form, all 10 swiper demo pages.
5. Run `pnpm build` and confirm it completes without new errors (per `CONTRIBUTING.md`'s "main is always buildable" rule).
6. Run `pnpm lint` and fix only lint regressions directly introduced by the bump (not pre-existing lint debt — out of scope).
7. Record the actual command output and what was observed for each verification step in `tasks.md`, per `AGENTS.md`'s "never invent verification that wasn't performed."
8. Rollback strategy: this is a version-only change with no data migration; rollback is `git revert` of the single commit plus `pnpm install` to restore the prior lockfile — no additional cleanup needed.
